## Context

Plan Windows Authenticode signing for Verkkokyylä release artefacts using the purchased Certum certificate, to establish publisher identity and reduce SmartScreen warnings over time. The current tag-release workflow publishes NSIS/MSI installers and a separately zipped standalone `verkkokyyla.exe`; it has macOS signing/notarization but no Windows signing. Certum PEM and DER files alone cannot sign because the matching private key is required. Until activation identifies the key’s custody, Certum’s documented SimplySign cloud path is the working assumption.

## Approach

1. Activate the purchased certificate and establish the private-key interface before enabling signing. Inspect the certificate in the Windows `CurrentUser\My` store and record: subject, SHA-1 thumbprint, Code Signing EKU, `HasPrivateKey`, expiry, and whether Certum exposes it through SimplySign, a cryptographic card, or an exportable PFX. PEM/DER are public certificate encodings; never convert, commit, or upload them as a substitute for a private key. If activation supplies a matching exportable private-key PEM/PFX and Certum authorizes CI export, use the PFX contingency at the end of this plan; otherwise use Certum’s virtual/card certificate by thumbprint.

2. Use **SignTool**, not Jarsigner, for this Tauri Windows application. Jarsigner signs Java/JAR artifacts and this release creates only Windows PE executables, MSI, and ZIP. Configure `src-tauri/tauri.conf.json` under `bundle.windows` with the activated certificate’s literal `certificateThumbprint`, `digestAlgorithm: "sha256"`, and `timestampUrl: "http://time.certum.pl"` so Tauri invokes SignTool during its normal Windows bundle build. Do not add a custom `signCommand`: Tauri’s native Windows signer selects the certificate from the current user store, exactly matching Certum’s documented SignTool `/sha1` flow. Enter that same literal thumbprint as the action’s `certum-key-id`; a mismatch must fail certificate availability before building.

3. Keep GitHub-hosted Windows automation, as selected. In `.github/workflows/release.yml`, before `tauri-apps/tauri-action` and only for `runner.os == 'Windows'`, pre-download `SimplySignDesktop-9.4.3.90-64-bit-en.msi` from Certum’s versioned official URL to the candidate action’s expected `SimplySignDesktop.msi` filename. Verify the downloaded MSI with `Get-AuthenticodeSignature` and fail unless `Status` is `Valid`; the action will reuse this pre-verified file instead of issuing its own download. Invoke `dismine/windows-app-signing-setup-action@89ae3b032d4bc7a5b98d1a42a34e61ecb6faad64 # v1.2.5` with `certum-username`, `certum-otp-uri`, and the matching `certum-key-id`, plus `capture-diagnostics: false`. The immutable action SHA is resolved from its current `v1` tag; use no mutable action tag.

4. Add only `CERTUM_USERNAME` and `CERTUM_OTP_URI` as GitHub secrets in the existing protected `release` environment. `CERTUM_OTP_URI` is signing-key-equivalent because it generates reusable SimplySign login codes; do not put it in repository files, logs, artifacts, or any environment other than `release`. The SHA-1 certificate thumbprint is public identifier material, not a secret. The chosen third-party action necessarily emits certificate-store metadata and accepts the TOTP seed, so it must remain tag-only and can run only after source review of the pinned commit; do not enable its screenshots/diagnostics or cache the installer.

5. Prevent unsigned artefacts becoming public. Change the existing matrix action’s `releaseDraft` to `true`; it still builds and uploads bundles, but the release remains private until verification. Immediately after the Tauri build in the Windows matrix leg, enumerate `src-tauri/target/release/verkkokyyla.exe`, `src-tauri/target/release/bundle/nsis/*.exe`, and `src-tauri/target/release/bundle/msi/*.msi`; run `signtool verify /pa /all /v` for each and fail for any invalid/missing SHA-256 RFC 3161 signature or unexpected Certum thumbprint. Only then run the existing `Compress-Archive` step, so the ZIP contains the already-signed raw executable, and attach it to the draft release. ZIP is not an Authenticode target.

6. Add a `publish` job that `needs: release`, has `contents: write`, uses the existing `release` environment, and runs `gh release edit "${{ github.ref_name }}" --draft=false`. GitHub’s default dependency rule means it runs only after every matrix build, including Windows verification and standalone upload, succeeds. Retain the release name/body creation in the matrix action and all current asset names; a failed Windows signing step leaves the draft unpublished rather than publishing unsigned Windows artefacts.

## Findings

- `.github/workflows/release.yml` is triggered by `v*` tags; one matrix `release` job runs on `windows-latest`, `macos-latest`, and `ubuntu-22.04`. `tauri-apps/tauri-action` builds and uploads release bundles at lines 74–89.
- Windows additionally zips `src-tauri/target/release/verkkokyyla.exe` at lines 93–98 and uploads `verkkokyyla_${version}_x64-standalone.zip` at lines 99–106. The README confirms the Windows download forms are NSIS/MSI installers plus the standalone ZIP (README.md:24–28).
- `src-tauri/tauri.conf.json` enables all bundle targets and declares `publisher: "tero-k"` (lines 24–34); its `bundle.windows` object is absent. Tauri documents `certificateThumbprint`, `digestAlgorithm`, and `timestampUrl` there, and signs generated installers and the application when the selected certificate exists in the runner’s store.
- Certum’s Code Signing in the Cloud guide requires SimplySign Desktop login and selects the certificate by SHA-1 thumbprint; its documented command is `signtool sign /sha1 "<thumbprint>" /tr http://time.certum.pl /td sha256 /fd sha256 /v "<file>"`. Microsoft requires `/fd` and `/td` in modern SignTool, recommends SHA-256, and documents `signtool verify /pa /all /v`.
- Certum publishes separate SignTool and Jarsigner guides. Jarsigner is irrelevant because the repository publishes no Java archive; SignTool is the correct PE/MSI tool.
- The supplied candidate is third-party and unaffiliated with Certum. Its `v1` tag currently resolves to immutable commit `89ae3b032d4bc7a5b98d1a42a34e61ecb6faad64` (`v1.2.5`); the reviewed composite action installs SimplySign Desktop, injects an automatically generated TOTP into the desktop GUI, and takes `certum-username`, `certum-otp-uri`, and `certum-key-id` inputs. It defaults diagnostics to off but prints certificate-store metadata. It skips its own download when `SimplySignDesktop.msi` is already present, enabling a prior Authenticode verification step.
- `tauri-apps/tauri-action` uploads its generated bundles while it builds. Consequently, a post-build check can gate publication only if the release is initially a draft. The action’s `releaseDraft` input supports that flow; a dependent job can publish after all matrix legs pass.

## Critical files & anchors

- `.github/workflows/release.yml` — official MSI preverification, pinned SimplySign automation, protected-secret scoping, draft-to-public release gate, Windows verification, and ZIP release order.
- `src-tauri/tauri.conf.json` — new `bundle.windows` SignTool settings.

## Verification

- Before editing the release workflow, activate the certificate on a disposable Windows account and run `Get-ChildItem Cert:\CurrentUser\My | Select-Object Subject, Thumbprint, HasPrivateKey, NotAfter` to confirm the expected Certum certificate is exposed with a usable private key. Then use Certum’s SignTool command on one locally built `verkkokyyla.exe` and run `signtool verify /pa /all /v` to establish the chain, timestamp, exact subject, and thumbprint.
- Trigger the revised workflow on a disposable version tag. The Windows setup must accept the pre-verified `SimplySignDesktop.msi`, find the matching certificate, and complete the Tauri build. Before the dependent publish job runs, `signtool verify /pa /all /v` must report `Successfully verified` for the raw executable, NSIS installer, and MSI; inspect their signer thumbprints and SHA-256 RFC 3161 timestamps.
- Confirm the GitHub release remains a draft until all three matrix legs succeed, then becomes public only through `publish`. Download `verkkokyyla_<version>_x64-standalone.zip`, extract it, and repeat `signtool verify /pa /all /v` for `verkkokyyla.exe`; its embedded signature must still verify after ZIP packaging. On a clean Windows VM, download and launch each release form; Windows must identify the Certum certificate subject as publisher. SmartScreen reputation is independent of signature validity and may still warn until the publisher/download reputation accumulates.

## Assumptions & contingencies

- The intended distribution remains the current Tauri NSIS/MSI bundles plus the standalone ZIP; no MSIX packaging or Microsoft Store submission is introduced.
- The selected integration assumes Certum activation results in a SimplySign cloud certificate. If it instead proves to be a physical card, GitHub-hosted automation is not applicable; replace the runner preparation with Certum’s card software on a protected self-hosted Windows runner, retaining Tauri’s thumbprint/SignTool configuration, draft gate, and verification steps. If it is an exportable private-key PFX that Certum permits in CI, replace SimplySign automation with base64 PFX and password GitHub `release` environment secrets, import PFX only into the ephemeral Windows user store, and retain the same Tauri, draft, and verification configuration.
